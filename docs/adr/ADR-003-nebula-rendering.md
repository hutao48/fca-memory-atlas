# ADR-003：星云渲染采用数据驱动体积 raymarch + 实例化星体 + HDR 后处理

- 状态：已接受（2026-11-12）
- 决策者：Lead（架构）+ Nebula 渲染组（原型对比执行者）
- 关联：ARCHITECTURE.md、PUBLIC_INTERFACE_FREEZE.md §5、docs/NEBULA_RENDERER.md（实测报告）

## 背景

视觉验收是核心项：拒绝普通节点图/固定星空背景/荧光塑料感；要求真实深空天文摄影质感、体积感、尘埃、远近层次、数据驱动（星云密度/颜色/尘埃必须与真实聚类与关系关联）。

## 候选方案

| 方案 | 思路 | 评估 |
|---|---|---|
| **A. 全屏体积 raymarch + 数据种子（主选）** | 半分辨率全屏 shader，FBM/Worley 3D 噪声，cluster 质心渲染为发射核，高频噪声做暗尘埃吸收，深度雾化 + HDR bloom + ACES | 质感最接近真实天文摄影；数据驱动自然；性能可调（半分辨率/步数/档位）；WebGL2 可承载 |
| B. 预烘焙星云纹理 + 2D 发光节点/连线 | CPU/离屏预生成一张或多张星云纹理，叠加星点与关系层 | 实现简单、性能好；但固定纹理易被看穿、数据关联弱、动态重排时伪影，作为低配/对比方案 |
| C. three.js 粒子星云 | 大量粒子 billboard 模拟气体 | 受粒子数与遮挡限制，体积感和尘埃结构弱，且引入第三方依赖 |

## 决策

以 **A** 为生产方案，**B** 为对比与低性能档的参考实现；必须实测两方案（视觉质量、100/1000/10000 节点性能、显存、CPU、缩放流畅度、低配档、高 DPI），把真实数据记录在 `docs/NEBULA_RENDERER.md`。渲染层分三部分：体积星云背景（数据驱动）、实例化星体层（记忆节点）、关系光丝/粒子层；后处理统一做 bloom/tonemap/暗角/颗粒/抖动。所有视觉映射必须可在图例/图层面板解释；`off` 档保留全部交互与标签可读性。

## 后果

- 必须做真实性能原型比较后冻结最终参数（不做“先写死背景图再补数据”的伪实现）。
- 数据契约以 Runtime `GET /graph` 为唯一输入；渲染器不得自造节点。
- 性能降级顺序：后处理 → 体积步数/分辨率 → 星点细节 → off 档。
